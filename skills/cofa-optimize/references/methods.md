# Solve, diagnose and verify

Exploit exact structure before generic search. A feasible baseline is useful for comparison and incumbent preservation; an exact solver can also find the first feasible solution. A failed construction does not prove infeasibility. Retain only independently validated incumbents; an improved objective with broken hard constraints is not an improvement.

For minimization, a feasible objective is an upper bound and a valid relaxation/exact method may provide a lower bound (reverse for maximization). Both must refer to the same full model and units. Record objective, valid bound when available, absolute gap or the solver's documented relative gap convention, solver/version, limits, tolerances, seed/thread settings and termination reason. A zero baseline makes percentage division undefined; an infeasible baseline is not a valid improvement comparator.

Exact search is exact only when it covers all relevant possibilities with valid bounds/pruning. Estimate DP/state/search growth before starting. Use a wall-clock/memory budget, preserve an incumbent on timeout, and leave time for service integration, validation, explanation and submission. Heuristics/local improvements may be appropriate when exact proof is intractable, but label them feasible/best-found/local, including the unmet proof requirement if relevant. Repeatable seeds do not ensure identical results across versions or machines.

Read the installed solver's status definitions. FEASIBLE does not establish global optimality; UNKNOWN or a time limit with no incumbent does not establish infeasibility. MODEL_INVALID requires fixing the model. INFEASIBLE refers to the submitted model: check accidental restrictions before asserting the business task impossible. OPTIMAL may reflect configured gap tolerances; report the precise guarantee. Unbounded and infeasible are distinct. A returned solution is not enough evidence for any of these claims.

Diagnose using a tiny instance, known feasible construction, units/index transformations and constraint families. Use conflict information where available. Diagnostic relaxations are not final valid answers to the original hard model; a sufficient conflict set need not be minimum. On repeated failure, record the observation, reconsider assumptions and choose a discriminating next experiment instead of changing weights blindly.

Recompute coverage, domains, constraints and objective from actual input and returned decisions, independently of solver totals. Reuse parsing/data definitions if appropriate, but do not merely ask the solver to validate its own totals. Compare tiny instances with hand calculation or bounded exhaustive oracle. Test required cases: impossible inputs, equality/tight limits, ties, zero/empty data where permitted, numerical precision, resource competition and altered inputs. Test service behavior with the actual algorithm path via `cofa-opt-service`. Choose relevant cases rather than a fixed benchmark quota.
